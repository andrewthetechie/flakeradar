# Intentional behaviour differences

Every way the Rust server intentionally differs from the Python server at commit `97b933d`. The rules are in `00-shared-context.md`, under "The compatibility rule". The parity tests treat each entry here as an allowed exception.

Add a row when you make a change. Removing or renaming a field, or changing a status code, needs the user's approval first.

## Pre-approved

| Area | Python | Rust | Why |
|---|---|---|---|
| Process model | `uvicorn --workers 2` | One process with a Tokio multi-thread runtime | Single binary. Leader election stays, for multiple replicas |
| MCP sessions | Session IDs per process | Stateless, no `Mcp-Session-Id` | Works across replicas. No tool uses session state. A consequence, measured: a `GET` or `DELETE` on `/mcp/` with no session header answers 400 `-32600 Bad Request: Missing session ID` in the reference and 405 `Method Not Allowed` here, because a stateless transport has no session to miss; a method neither serves, such as `PUT`, answers the same 405 in both |
| API docs | `/docs` Swagger UI and `/redoc` | Redoc at `/docs`. `/redoc` is gone | User decision. Redoc is read-only |
| Env var names | Case-insensitive | Uppercase only | Standard for a binary |
| Database URL | `?ssl=` (asyncpg) | `?sslmode=` (SQLx), with no translation | Fresh install. `postgresql+asyncpg://` prefixes are still accepted |
| Default bind | Set by the `uvicorn` command line | `127.0.0.1:8000` unless configured | Reads are unauthenticated by design |
| JSON numbers | `pydantic` float text | `serde_json` float text | Same values |
| Timestamps | Fraction omitted when zero | Always six fractional digits | Fabro and the frontend accept both |
| `{raw!r}` in error text | Python escaping | Single quotes around the raw value | Only unusual characters differ |
| `line` attribute | Unicode digits pass `isdigit()`, and some then crash `int()` | ASCII digits only, anything else is no line | Removes a crash |
| Report `error` text | `ExceptionType: message` | A Rust error description, same 2000-character cap | Text is for humans |
| Startup on Alembic databases | Upgrades them | Refuses to start | Fresh-install cutover (ADR 0010) |

## Added during the port

| Task | Area | Python | Rust | Why |
|---|---|---|---|---|
| 02 | A `<testcase time>` attribute that is not a number | junitparser's `time` property runs `float(...)`, so `parse_junit_xml` raises an unhandled `ValueError` and `POST /api/ingest` answers 500 and stores nothing | Validates the attribute and answers 400 with the usual `{"detail": …}` JSON body (`application/json`), where the detail is the typed `InvalidTime` message | **Approved by the user on 2026-11-04.** A 400 is deliberate: the code standards forbid panicking on untrusted CI input, and a 500 is not a contract anyone can rely on. A missing, empty, negative or fractional `time` keeps Python's behaviour (0.0, or the value parsed). Because the status changes, the golden's `body` (`Internal Server Error`) and `content-type` (`text/plain; charset=utf-8`) differ too; the allowance names those fields of that one golden, no others |
| 04 | The `line` attribute | Unicode digits pass `isdigit()`, so the Arabic-Indic `line="١٢"` in `non-numeric-line.xml` becomes line 12 (13 with `line_base=0`) | ASCII digits only, so that value is no line (`null`) | The pre-approved rule above, recorded here because two JUnit goldens change in exactly this field. The allowance in `allowed-differences.json` names the case and both `line_base` values |
| 02 | The suffix of a JUnit parse-error detail | `"Not a valid JUnit XML report: "` + the ElementTree/expat message, such as `syntax error: line 1, column 0` | `"Not a valid JUnit XML report: "` + the `roxmltree` message | The prefix and the 422 status are the contract, and they stay. The parsers' own wording cannot be reproduced, and rewriting expat's messages would be worse than saying which parser rejected the file. `"Report parsed but contained no test cases."` is hand-written and stays identical |
| 06 | The `detail` for a `multipart/form-data` body whose framing cannot be read | Starlette raises `MultiPartException("Invalid multipart data.")` around the `python_multipart` error, and FastAPI answers 400 with that detail. A part left open when the body ends is not an error at all: the form simply has no `report` field, and the route answers 400 `{"detail": "Empty report body"}` | Also answers **400**, with the hand-written `{"detail": "Empty report body"}` | The route reads the buffered body itself instead of handing it to a form parser, so a form the reference parser refuses and a form that arrives with no `report` file are the same thing to it: an upload with nothing in it. The status is the contract; `Invalid multipart data.` is Starlette's wrapper around `python_multipart`'s own error, which nothing can reproduce without reimplementing its parser. Verified against `starlette.formparsers.MultiPartParser` 1.10.0: it skips any run of leading CR or LF and then wants the delimiter, so a form behind `\n` or `\r\n\r\n` is fine and a first byte that is anything else is an error; it refuses bare-LF framing; and it needs no closing delimiter, because `python_multipart`'s `finalize()` is a no-op (`multipart.py:1578-1590`), so a part still open at the end simply yields no field — a 400 either way |
| 06 | A `ci_run_attempt` number past the column's range | asyncpg raises on the value, so `POST /api/ingest` answers 500 and queues nothing | Validates the range (Pydantic's `ge=1` plus the `int4` column's maximum) and answers **400** with the usual `{"detail": …}` body, where the detail is `ci_run_attempt must be at most 2147483647`. Nothing is queued, and no Repo or Project row is created | **Approved by the user on 2026-11-04.** The same treatment the `time` row above got: a crash is not a contract, and CI data must not be silently rewritten into a value CI never sent (which is what the earlier saturating row in this port did). A real CI attempt count is a handful of digits. No recorded golden carries such a value |
| 11 | The MCP result envelope | fastmcp's results carry an explicit `null` for every absent optional field: `_meta` on the result, `annotations` and `_meta` on each content block, each annotation hint a tool does not set, `execution` and `icons` on a tool, and the unset capability and `serverInfo` members of `initialize`. `serverInfo.version` is fastmcp's own version (`4.1.6`), `capabilities.logging` is `{}` and `capabilities.resources.subscribe` is `false` | rmcp omits an absent optional field instead of writing `null`, does not advertise the deprecated `logging` capability, and reports FlakeRadar's own version (`2.0.0`). `tools/list` additionally carries the SEP-2322 `resultType` and the SEP-2549 `ttlMs`/`cacheScope`, because fastmcp omits all three from its `tools/list` answer: its `tools/call` results do record `resultType: "complete"` (goldens `mcp/07`–`46`), but none of them carries `ttlMs` or `cacheScope`, and the `tools/list` golden (`mcp/06`) records none of the three | The contract is the tool names, titles, descriptions, input and output schemas, annotations, and the `content`/`structuredContent`/`isError` of an answer, and every one of those is compared unchanged. An absent field and an explicit `null` are the same value to a client, and no client reads fastmcp's own version. Each allowance names exactly one field of one MCP golden: the answer's `content[].text` is still compared character for character (with the recorder's `<timestamp>`/`<date>` placeholders filled), and a renamed field or a changed description still fails |
| 11 | The text of two MCP failure results | fastmcp 4.1.6 answers a tool that raises with HTTP 200 and a JSON-RPC **result** carrying `isError: true`, one text block, and no `structuredContent`: `Error calling tool 'list_repos': (sqlalchemy.dialects.postgresql.asyncpg.ProgrammingError) relation "repos" does not exist` followed by the rendered `[SQL: …]`, the bound `[parameters: …]` and `(Background on this error at: https://sqlalche.me/e/21/f405)`. Arguments that do not validate answer the same shape, with `1 validation error for call[<tool>]`, the field, and Pydantic's diagnosis ending in `[type=int_parsing, input_value='many', input_type=str]` and an `errors.pydantic.dev` link | Answers the same status, envelope, prefix, field and diagnosis for both, with the failure's own message: `Query Error: error returned from database: relation "repos" does not exist` for the raising tool, and serde's `invalid type: string "many", expected i64` for the argument, with `arguments` where Pydantic names the field of a failure that is the argument object itself | The status, the envelope, the `isError` flag, the header, the field line and the underlying failure are the contract and they match. SQLAlchemy's exception class, its rendered SQL (SeaORM renders different statements), its bind-parameter list and its `sqlalche.me` link, and Pydantic's `[type=…, input_value=…, input_type=…]` taxonomy with its `errors.pydantic.dev` link, cannot be reproduced without inventing text this port did not produce. Unknown tool names (`Unknown tool: 'x'`), the two raising-tool shapes and the parse-error answer match the reference exactly, and no committed golden records any of them, so no replayed step's comparison changes. Measured by driving the pinned fastmcp app over a loopback port |
| 11 | A `POST /mcp/` body that is JSON but not a JSON-RPC message | Answers **400** with `-32602` and `Validation error: 11 validation errors for union[JSONRPCRequest,JSONRPCNotification,JSONRPCResponse,JSONRPCError]`, then Pydantic's report per member (a `{"hello": 1}` body gives 11 errors, `[]` gives 4) | Answers **415** with rmcp's plain-text `fail to deserialize request body …`, the answer this transport gives any body it cannot read as JSON-RPC | Both are protocol errors and no golden pins either shape, but the reference's text is Pydantic's union report over the MCP SDK's four message models, which nothing in this port models closely enough to reproduce, and this task's brief was scoped to the tool-execution and parse-error cases. Recorded rather than silently differing; the JSON states that can reach this port's MCP clients are well-formed requests |
| 12 | The headers and the `ETag` of a file the frontend serves | Starlette's `StaticFiles(directory=dist, html=True)` read the file from disk: `etag` was `"<md5 of mtime-size>"`, `last-modified` came from the file's mtime, `accept-ranges: bytes` came with `Range` support, `If-Modified-Since` was honoured, and no `Cache-Control` was sent at all | The same media types, including Starlette's `charset=utf-8` on `text/*`, but the `ETag` is the quoted SHA-256 of the file's bytes, there is no `last-modified` (an embedded file has no mtime) and no `Range` support, so a client revalidates with `If-None-Match` rather than a date; and the cache policy is the one this task's brief asks for: `Cache-Control: public, max-age=31536000, immutable` for everything under `assets/`, whose names Vite hashes, and `no-cache` for the rest, which leaves `index.html` revalidated on every load | The bytes, the media types, the statuses, `HEAD`, and the 304 on a revalidation are the contract and they match. An embedded file has no modification time, so a content hash is the only identity it can offer, and `last-modified` would be a lie. A year is safe only because a hashed name's content never changes; `index.html` is the one file that does, so it must be revalidated. `Range` requests are not something a browser sends for a bundle or a font |
| 12 | A static path that climbs out of the frontend's root | `StaticFiles` normalised `..` away before the lookup, so `GET /assets/../index.html` served `index.html` | Answers the API's 404 for a decoded path with a `..` segment, a backslash or a NUL, without asking the source | The task's brief says to reject path traversal. Nothing a browser asks for has a `..` in it, and a request that has one is not a request for a page, so the stricter answer costs nothing and removes the question of whether a normalisation is correct. Encoded forms (`%2e%2e`, `%2f`, `%5c`) are decoded first and refused the same way |
| 12 | A method other than `GET` or `HEAD` on a path the frontend does not hold | With `frontend/dist` mounted, `StaticFiles` raised 405 for every unmatched path whose method was not `GET` or `HEAD`, so `POST /nowhere` was 405 and `GET /nowhere` was 404; with no `dist` both were 404; and the same mount matched before Starlette's `redirect_slashes`, so `GET /api/tests/` was a static-file 404 rather than the 307 a build with no `dist` gave | 405 for a path the frontend does serve (`POST /assets/index-abc.js`), and the API's 404 for one it does not, whether or not a frontend is embedded | The reference's answer depended on whether a directory happened to exist on the machine it ran on, which a single binary must not. The status the two agree on is the one for a path that exists, and that is the case a client can act on. Nor does the API keep the reference's trailing-slash 404: `/api`, `/mcp` and `/metrics` never reach the assets here, so `GET /api/tests/` keeps the 307 the reference gave whenever `dist` was absent, and the client is sent to the path that answers |
| 13 | The process's command line | `uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 2`, so the reference's own surface is uvicorn's: `--host`, `--port`, `--workers`, `--log-level`, `--reload` and the rest of its flags, and every setting that is not a flag came from `FLAKERADAR_*` (or `.env`) | One binary whose command line is `flakeradar [serve\|healthcheck]`, `--version` and clap's `--help`; it serves with no argument, and the bind comes from `FLAKERADAR_HOST` and `FLAKERADAR_PORT`. There is no flag for a setting | The binary interface is settled in `00-shared-context.md`: env and `.env` config only, one process, no reload. uvicorn's flags configure uvicorn — its worker count, its event loop, its log formatter — and none of them names a FlakeRadar setting, so carrying them over would describe an interpreter this port does not have. The image passes the same values through `FLAKERADAR_HOST=0.0.0.0` and `EXPOSE 8000`, so a deployment's answer is unchanged |
| 13 | The exit status of a refused start-up | uvicorn's `STARTUP_FAILURE` constant, **3**, whether the refusal is the shipped default token, an unreadable setting, a database URL that is not PostgreSQL or an Alembic database (measured: `FLAKERADAR_API_TOKEN=changeme` with the app's lifespan, `ERROR: Application startup failed. Exiting.`, exit 3) | **1**, clap's own status (2) for a command line it cannot parse, and 0 for a clean shutdown after SIGTERM or Ctrl-C | Any non-zero status stops a container or a service unit the same way, and 3 is uvicorn's internal code for "lifespan failed", not a number FlakeRadar chose or documents. Reproducing it would pin this port to an interpreter constant. The `healthcheck` subcommand keeps the status that matters to a probe: 0 when `/api/health` answers 200, 1 otherwise |
| 14 | The `/openapi.json` document | FastAPI's generated document: FastAPI's own summaries, operation ids (`health_api_health_get`), Pydantic's schema spelling, its framework components `HTTPValidationError` wrapping `ValidationError`, and a `x-api-key` header parameter on every route that depends on the token | utoipa's generated document: the `#[utoipa::path]` annotations' summaries and tags, utoipa's schema spelling, `ValidationIssue` carrying the same five issue fields (`type`, `loc`, `msg`, `input`, `ctx`), and the same `x-api-key` header parameter, documented on the nine token-protected routes although the token is a middleware layer rather than an extractor | The two documents are generated by different frameworks from different source, so their prose, operation ids and schema spelling cannot agree. What both promise a client is the contract the replay checks: the same 23 paths, the same methods on each path, the same parameters on each operation, the same field names in every response schema, and the same schema name on every 2xx body. The reference's two validation schemas are its framework's own: `ValidationError` is the port's `ValidationIssue` under another name and with the same fields (checked), and `HTTPValidationError` wraps it in `detail`, which this port documents as the status's description because the 422 replay steps already compare the wire body. `tests/parity.rs` compares exactly those five things and reports any other difference by path or schema |
